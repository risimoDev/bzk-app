## 1. Что это

Полное переписывание сайта рекламно-производственного агентства «БЗК
Принт» (Пермь). Старый сайт на PHP лежит в корне репозитория
`C:\Projects\bzk`, новый - в `C:\Projects\bzk\bzk-app`.

Next.js 16 (App Router, Turbopack) · TypeScript · Drizzle ORM ·
PostgreSQL 17 · Tailwind CSS 4 · Auth.js v5 · Docker Compose за Caddy.

Данные перенесены из боевой MySQL скриптом `scripts/migrate-data.mjs`.
Дамп старой базы - `schema.sql` в корне старого репозитория
(`C:\Projectszk\schema.sql`). С ним же сверяется
`npm run verify-restore`. Путь ищет `scripts/schema-dump.mjs` по списку
мест - после переезда папки жёсткая ссылка `../schema.sql` перестала
работать; переопределяется переменной `SCHEMA_DUMP`.

**Весь `bzk-app/` не закоммичен** - в git он числится как `?? bzk-app/`.
Коммитов не делали и не просили.

**Про Next.js 16 отдельно.** Это не тот Next, который помнит модель:
в шестнадцатой версии middleware переименован в **Proxy**, и
`src/proxy.ts` с экспортом `proxy()` - штатное соглашение, а не
самодеятельность. Заводить `middleware.ts` не нужно и нельзя.
Документация лежит прямо в проекте:
`node_modules/next/dist/docs/01-app/01-getting-started/16-proxy.md`.
Перед правкой чего-то каркасного читай оттуда, а не по памяти - об этом
же говорит `AGENTS.md`. Что CSP действительно накладывается, видно в
сборке строкой `ƒ Proxy (Middleware)` и в заголовках ответа.

## 3. Договорённости с заказчиком - не нарушать

- **Позиционирование.** «Мы не типография, а рекламно-производственное
  агентство, у нас есть часть своего оборудования, но по большей части мы
  перезаказываем. Акцентировать внимание на том, что мы перезаказываем, не
  надо, но и врать в текстах тоже не надо.» Тексты витрины писать с учётом
  этого.
- **Редактор открыток** - отдельная функция кабинета для Федерации
  кикбоксинга, не редактор макета. Включается флагом `users.can_use_editor`
  отдельным клиентам.
- **Промпты писать в чат**, а не создавать под них страницы: «пиши тут в
  чате, чтобы я мог скопировать».
- **Этапы делать по порядку**, полностью, потом дорабатывать мелочи.
- **Выгрузка в 1С отложена намеренно.**
- Заказчик просил закрыть весь список за один запрос, не разбивая.
- **Документы клиенту показывает менеджер.** Счёт и УПД не должны быть
  видны клиенту сразу: их открывают после всех уточнений по составу и
  сумме. Реализовано флагом, см. §6.

## 4. Соглашения в коде

**Комментарии и тексты - по-русски.** Комментарий объясняет *почему* так
сделано, а не что делает строчка. Пиши их там, где читатель споткнётся и
спросит «почему», и не пиши там, где всё очевидно. Тексты интерфейса -
человеческие, без канцелярита и рекламы.

**Серверные действия.** Файл начинается с `"use server"`. Каждая
экспортируемая функция - это открытый эндпоинт, поэтому **у каждой** должна
быть проверка прав `can(module, action)` или `currentUser()`. Исключения
только два и они намеренные: `src/app/actions/cart.ts` (корзина анонимная) и
`logout` в `session.ts`.

**Типы маршрутов** - `PageProps<"/route">`, `LayoutProps<"/">`,
`RouteContext<"/api/...">`, генерируются `npx next typegen`.

**Формы** - `useActionState`. Форма состояния обычно
`{ ok: boolean; message?: string }` либо
`{ ok?; error?; fieldErrors?: Record<string,string> }`.

**Разделение чистого и серверного.** Клиентский компонент не должен тянуть
`pg` в браузерный бандл. Если словарь нужен и форме, и запросу - чистая
часть лежит в `src/lib/x.ts`, работа с базой в `src/lib/x-db.ts` с
`import "server-only"`. Так уже сделано: `company.ts`/`company-db.ts`,
`seo.ts`/`seo-db.ts`, `client-portal.ts`/`client-portal-db.ts`,
`counterparties.ts`, `promocodes.ts`/`promocodes-db.ts`,
`documents.ts`/`documents-meta.ts`, `rate-limit.ts`/`client-ip.ts`.

**Что нельзя тянуть в проверочные скрипты.** Скрипты запускаются под
голым node с `--experimental-strip-types`, а он не умеет параметры-свойства
конструктора (`constructor(readonly wait: string)` в `src/auth.ts`).
Поэтому модуль, который нужен скрипту, не должен импортировать `@/auth`.
Ради этого `order-access.ts` (знает текущего пользователя) и
`order-documents.ts` (чистый предикат по базе) разведены.

**Админка** - компоненты `AdminPage`, `AdminStat`, `AdminEmpty` из
`src/components/admin/AdminPage.tsx`. Плотная вёрстка, без витринного
коллажа. Витрина - коллаж по брендбуку 2026, компоненты в
`src/components/site/` и `src/components/ui/`.

**Классы полей формы** - в `src/components/ui/form-classes.ts`:
`siteLabelClass`, `siteInputClass` для витрины и кабинета,
`adminLabelClass`, `adminInputClass`, `adminInputOnPaperClass`,
`adminInlineInputClass` для админки. Раньше строка копировалась в 30
файлов; новые формы берут классы оттуда, а не копируют.

**Удаление - только через `ConfirmButton`** (`src/components/ui/ConfirmButton.tsx`).
Без `onConfirm` это кнопка отправки формы: после подтверждения она
нажимается ещё раз и форма уходит обычным путём, с `useActionState`.
С `onConfirm` - просто вызывает функцию. В окне пишем, что именно
пропадёт и пересчитается.

**Списки в админке листаются** через `AdminPager` + `pageFrom`/`offsetOf`
(`src/components/admin/AdminPager.tsx`). Молча обрезать выборку `.limit(N)`
нельзя: запись за пределом просто исчезает из виду. Два списка на одной
странице - у второго свой параметр (`param="rpage"`).

**Цветовые токены Tailwind:** `paper bone ink brand brand-bright ok warn
danger navy ice graphite`. Прозрачность через `/12`, `/45` и т.п.

## 5. Грабли - уже наступали, не наступать снова

**Drizzle**

1. **Колонки внутри `sql` в списке выборки рендерятся без имени таблицы.**
   Коррелированный подзапрос молча сравнивает колонку саму с собой и
   возвращает мусор. Ловилось трижды. Решение: отдельный сгруппированный
   запрос + `Map` по id.
2. `onConflictDoUpdate({ set: ... })` принимает **camelCase** имена свойств
   (`ogTitle`), а не имена колонок.
3. `db.transaction` есть, `.for("update")` работает - использовать для
   счётчиков и приёмки.
4. **Прямое соединение по «главной картинке» даёт дубли.** Ничто в схеме
   не мешает товару иметь две записи `product_images.is_main = true`, и
   тогда `leftJoin` вернёт товар дважды. И каталог, и `/api/products`
   берут картинку сгруппированным подзапросом `catalogImages()` из
   `lib/product-images-db.ts` - делай так же.
   Там же и разделение по `product_images.kind`: `logo` - картинка для
   каталога, всё остальное - фотографии готовых работ для карточки
   товара. У перенесённых со старого сайта записей `kind = 'photo'`.

**Названия колонок, где легко ошибиться**

| Ожидаешь | На самом деле |
|---|---|
| `products.isActive`, `updatedAt` | `isHidden`, `createdAt` |
| `external_order_items.price` - цена за штуку | **сумма строки целиком** |
| `qc_inspections.production_stage_id` → справочник | → `production_order_stages` (строка конкретного заказа) |
| `qc_checklists.stage_id` | → `production_stages` (справочник) |
| `order_promocodes.promocodeId` | связь по строке `promo_code` + `applied_discount` |
| `documents.type` | `doc_type` |
| `promocodes.start_date` / `end_date` | `timestamp`, а не строка - см. п. 23 |

**Права**

- Действия `delete` у модуля `messaging` нет ни у одной роли - используется
  `messaging.edit` (он только у администратора).
- Полная матрица прав в таблице `role_permissions`, см. §9.

**Next / React**

5. ESLint запрещает `setState` синхронно внутри эффекта.
6. Turbopack ругается на динамический доступ к файловой системе - внутри
   `path.resolve` ставится `/* turbopackIgnore: true */` (см. `lib/uploads.ts`).
7. `next/headers` нельзя импортировать в проверочных скриптах - поэтому
   `clientIp()` вынесен в отдельный `lib/client-ip.ts`.
8. **Изменения `next.config.ts` требуют перезапуска сервера разработки**,
   иначе редиректы остаются старыми. Правила лежат в `src/lib/redirects.ts`,
   но подключаются через конфиг - то же самое.
9. **301 браузер кеширует намертво.** Если отдал неверный 301, он застрянет
   у всех, кто успел зайти. Для проверки - другой параметр в адресе.
10. ESLint не ругается на неиспользованный аргумент, если после него есть
    использованный (`_prev, formData`), но ругается, если не используются
    оба. Либо используй, либо объявляй один параметр.

**Маршруты и редиректы**

11. Общее правило вида `to("/admin/offers/:path+", …)` перехватывает и
    новые страницы раздела. Заводя `/admin/<раздел>/new`, сначала
    прогонять `npm run check:redirects` - он это ловит. Так уже
    поймалось трижды: `offers/new`, `suppliers`, `checkout`.

**Drizzle-kit push**

12. Имена внешних ключей, которые генерирует Drizzle, бывают длиннее 63
    знаков, и Postgres их обрезает. После этого `push` их не узнаёт и
    каждый раз печатает те же `ADD CONSTRAINT`. Ключи при этом на месте -
    проверять через `pg_constraint`, а не по выводу push.

**Проверка в браузере**

13. `form.requestSubmit()` в React 19 **часто не запускает** серверное
    действие. Нажимать `form.querySelector('button[type=submit]').click()`.
14. Область просмотра иногда схлопывается в 0×0 (`read_page` возвращает
    пустую страницу) - помогает `resize_window` с `preset: "desktop"`.
15. `resize_window` с явными числами ломает координаты кликов: панель
    показывает страницу в своём масштабе, а `ref`-клик считает координаты
    в размерах эмулированного окна, и нажатие уходит мимо - молча.
    Возвращать `preset: "desktop"` и кликать по координатам со свежего
    снимка.
16. Когда окно приложения за другим окном, снимок приходит пустым, а
    `screenshot` иногда истекает по таймауту. DOM при этом жив: работают
    `get_page_text`, `find` и `javascript_tool`. Надёжнее всего заполнять
    формы через `javascript_tool` - установкой значения через
    `Object.getOwnPropertyDescriptor(...).set` и событием `input`, иначе
    React не заметит ввода.
17. Локальные файлы (`file://`) инструментами браузера не управляются.
18. Буфер консоли инструмента не чистится - старые ошибки выглядят как
    новые. Для чистой проверки открывать новую вкладку.
19. `<select defaultValue>` после `revalidatePath` показывает прежнее
    значение: React не трогает уже существующий узел. Ставить
    `key={String(current)}`, чтобы поле пересоздалось.

**Деньги и перенесённые данные**

20. Строку автоматического расчёта себестоимости старый сайт подписывал
    иначе («Автоматический расчет себестоимости материалов», а у внешних
    заказов ещё и «(коррекция внеш.)»). Пересчёт, который ищет только
    свою подпись, старую строку не находит и дописывает вторую -
    себестоимость удваивается. Список подписей - `LEGACY_AUTO_EXPENSE`
    в `lib/accounting-db.ts`.
21. **Номера заказов пересекаются.** `orders` и `external_orders` - две
    последовательности, и «заказ № 17» означает два разных заказа. Везде,
    где номер уходит в адрес или в документ, рядом обязан идти источник
    (`site` / `external`). Из-за этого печатные формы живут по адресам
    `/print/invoice/[source]/[id]`, а номер документа у менеджерского
    заказа помечен буквой: `81-М`.
22. `orders.contact_info` - это JSON, а не строка: контакты на момент
    заказа плюс `is_urgent`, `original_total_price`, `urgent_fee`,
    `promo_data`. Разбирает `lib/order-contact.ts`. Формат сохраняем как
    у старого сайта.
23. `promocodes.start_date` и `end_date` - `timestamp`, а не строка.
    Код вида ``new Date(`${p.startDate}T00:00:00`)`` давал Invalid Date;
    даты в базе были пустые, и это не всплывало до появления формы.
    Срок действия сравнивается по календарным дням, а не по моментам
    времени: «до 20 января» - это весь двадцатое.

**Скрипты и оболочка**

24. Разбор `.env` в скриптах: **сначала отрезать комментарий, потом кавычки**,
    иначе в значении остаётся хвостовая кавычка (на этом уже терялся
    `AUTH_SECRET`, и подпись считалась другим секретом).
25. `scripts/alias-loader.mjs` + `alias-hooks.mjs` дают `@/`-импорты под
    голым node: сначала `src/x.ts`, потом `src/x/index.ts`. Пакет
    `server-only` подменяется заглушкой.
26. Скрипту, который лезет в базу, `.env` нужно читать самому - примеры
    в `check-password-reset.mjs` и `check-documents-access.mjs`.
27. Большие `.tsx` через heredoc в Bash пишутся ненадёжно - использовать
    инструмент Write. Точечные правки удобно делать питоном, но
    **скрипт правки записывать в файл, а не в heredoc**: `python - <<'PY'`
    спотыкается о длинные вставки, а `\n` внутри строки превращается в
    настоящий перенос. Надёжнее: записать скрипт правки в scratchpad
    инструментом Write и запустить `python <путь>`.
    `perl -pi -e` однажды покорёжил многострочный блок импортов.
28. Кириллица в поле `type="email"` не проходит проверку браузера - в
    тестовых адресах использовать латиницу.
29. `process.exit()` в скриптах на Windows роняет воркер модульных хуков -
    использовать `process.exitCode`.
30. Классификатор прав может заблокировать смену пароля пользователя и
    повышение роли через Bash. Если это случилось - не обходить, а
    попросить заказчика войти в браузере самому.
31. **Docker Desktop падает сам** - база пропадает посреди работы, и
    витрина висит: шапка читает сессию и корзину. Теперь вместо пустого
    экрана страницы ошибок (`error.tsx`, `global-error.tsx`), но первым
    делом при странном поведении - `docker ps`.
32. ESLint (`react-hooks/purity`) не пускает `Date.now()` в теле серверного
    компонента. `new Date()` - можно; от него и считать границы дат.
33. JSX-комментарий `{/* … */}` перед элементом внутри `( … )` тернарного
    выражения - это второй элемент в скобках и синтаксическая ошибка.
    Комментарий ставить внутрь обёртки.
34. Питон в консоли Windows печатает в cp1251 и падает на «✓». Скрипты
    правок запускать с `PYTHONIOENCODING=utf-8`.
35. `public/logo.svg` размечен в миллиметрах: sharp при `density: 600`
    получает растр больше своего предела. Хватает `density: 150`.
37. **Проверочные скрипты не должны удалять папки хранилища.**
    `check:product-images` в конце стирал `storage/uploads/products`
    целиком - и вместе с ним все 33 загруженных логотипа (восстановлены
    повторным переносом из `assets-src/products/_imported`). Теперь
    `check:uploads` и `check:product-images` запоминают, была ли папка до
    проверки, и удаляют только её, если создали сами.
36. В `.env` разработки SMTP заполнен настоящим ящиком. Письма клиентам о
    статусе теперь уходят на их адреса из базы - **при ручной проверке не
    менять статусы заказов реальных клиентов**, проверять на своём
    тестовом аккаунте.
38. **Восстановление базы - только `bash deploy/restore.sh [файл]`.**
    Все копии - формат custom (`pg_dump -Fc`, файл `.dump`): ночная
    (`bzk-….dump`), ручная (`backup-now.sh`, `postgres-….dump`) и
    страховочная перед деплоем (`pre-deploy-….dump`). Старые копии до
    перехода - `….sql.gz`. Скрипт понимает оба формата. Прежний рецепт
    `gunzip -c … | psql` на живой базе не годится: простой SQL не
    удаляет старые таблицы (ошибки «уже существует», дубли), а пустой
    `.sql.gz` - его оставлял старый `pg_dump | gzip`, когда дамп падал, -
    молча давал пустую базу. `restore.sh` до остановки приложения
    проверяет полноту (`gzip -t` и строка `-- PostgreSQL database dump
    complete`; для `.dump` - `pg_restore --list`, наличие TABLE DATA и
    полное чтение), пересоздаёт схему `public` и грузит дамп одной
    транзакцией, а `COMMIT` дописывает, только если строка окончания
    прошла через поток. Ctrl+C и обрыв ssh поднимают приложение обратно
    (`trap`).
39a. **Деньги заказа считает только `recalcOrderMoney`**
    (`lib/order-money-db.ts`, правила - в `lib/order-money.ts`). Любое
    действие, которое задевает позиции, срочность, корректировку, статус,
    платёж или расход, зовёт его в своей транзакции: он пересчитывает
    доход, расход («факт вытесняет оценку»: при строках `is_write_off`
    оценка в расход не входит), налог, статус оплаты (только из
    `order_payments`; у заказа менеджера копируется в
    `external_orders.status`) и `orders_accounting.is_cancelled`. Писать
    эти поля руками нельзя - разойдутся.
    - **Итог заказа** пересобирается из позиций только с
      `{ rebuildTotal: true }` - при правке позиций, срочности,
      корректировки и при оформлении. Платёж, расход, смена статуса берут
      сохранённый итог: у перенесённых заказов contact_info бывает в
      другом формате, и пересборка молча поменяла бы сумму из счёта.
      Итог заказа менеджера = позиции + `adjustment`; если скидка больше
      позиций, действие отказывает (`totalClamped`).
    - **Статус заказа** - только через `changeOrderStatus` (таблица
      переходов в `lib/order-status.ts`). Производство зовёт его с
      `{ system: true }`: таблица не действует, но отменённый заказ цех не
      оживляет.
    - **Блокировки** - `FOR NO KEY UPDATE`, не `FOR UPDATE`: вставка
      платежа/расхода/позиции держит KEY SHARE на родителе, и FOR UPDATE
      давал взаимную блокировку двух параллельных платежей (сценарий есть
      в `check:money`). FOR UPDATE остался только при удалении заказа.
    - Отчёты исключают `is_cancelled`, долг = доход − платежи
      (`openDebt`), месяцы - по Asia/Yekaterinburg (`REPORT_TZ`,
      `reportMonthStart`).
    - **`npm run recalc-accounting`** приводит старые карточки к правилам
      (`--apply` - записать; повторный запуск ничего не меняет). Статус
      «оплачен» он берёт тот, что видели люди (`external_orders.status`,
      иначе карточка), сначала превращает оплаченные счета Точки в
      платежи, потом заводит платёж-перенос на остаток. Отменённым
      переноса нет - только строка в отчёте. Итоги заказов не трогает;
      если тронул бы - `--apply` отказывает с кодом 2. Оценку себестоимости
      считает заново только там, где её строки нет. **На сервере его
      запускает `deploy/deploy.sh` сразу после `drizzle-kit push`, до
      запуска нового приложения**; после `migrate-data.mjs` - руками
      (DEPLOY.md). Адрес базы - через `scripts/db-url.mjs`: в контейнере
      `tools` файла `.env` нет.

41. Bash-инструмент агента в heredoc превращает `\\` в `\`. Python-скрипт

42. **Правила удаления (ON DELETE) - историю не стираем.**
    - `order_items.product_id`, `external_order_items.product_id` -
      `set null`: товар можно убрать, позиция остаётся со снимком в
      `item_name` (и `order_items.unit`).
    - `order_expenses.order_item_id` - `set null`: расход принадлежит
      карточке заказа, а не позиции.
    - `orders.user_id` - `restrict`: клиента с заказами удалить нельзя.
      Удаления пользователей в приложении нет вообще (ни действия, ни
      страницы; `account_deletion_requests` только заведена в схеме) -
      человека убирают блокировкой.
    - `orders_accounting.order_id` - `restrict`: бухгалтерия не исчезает
      вместе с заказом, а заказ с карточкой удалить нельзя - его
      отменяют. Если заказ всё же надо стереть (тестовый в скрипте),
      сначала удалить карточку: `delete from orders_accounting where
      order_id = …` (так сделано в `check:money`). Заказы менеджера
      уже работали так: `deleteExternalOrderChecked` удаляет карточку
      явно и только без платежей и списаний.
    - Сотрудник, оставивший след, не удаляется: `tasks.created_by`,
      `qc_inspections.inspector_id`, `qc_defects.reported_by`,
      `mass_messages.created_by` - `restrict`; `chat_messages.user_id`,
      `support_ticket_messages.user_id`, `task_comments.user_id` -
      `no action` (то же, но проверка в конце оператора: при удалении
      клиента каскад сначала уберёт его чаты и обращения вместе с
      сообщениями, а сообщение сотрудника в чужом обращении по-прежнему
      не даст удалить сотрудника). Обе формы дают ошибку 23503, а не
      23001. Проверка - `check:db-rules` (читает `pg_constraint` и
      пробует удалять).
    - Остальные `cascade` оставлены осознанно: это личные данные самого
      клиента (уведомления, корзина склада, отзывы, обращения), а не
      бизнес-история.
43. **Номера считает счётчик, а не `count(*) + 1`.** Закупки
    («ЗК-2026-007»), КП («КП-2026-0007»), обращения («TK-20261028-0003»)
    и документы по шаблону («СЧ-2026-0007») берутся из таблицы `counters`
    (`key`, `value`), функцией `nextNumber` в `lib/numbering-db.ts`:
    один `INSERT … ON CONFLICT DO UPDATE` под блокировкой строки.
    Ключи - `purchase:ГГГГ`, `offer:ГГГГ`, `ticket:ГГГГММДД`,
    `doc:<префикс><год>` (`lib/numbering.ts`). Счётчик сам догоняет
    наибольший существующий номер (в том числе вписанный руками) и
    не откатывается ниже него, поэтому отдельной миграции данных боевой
    базе не нужно; начальные значения всё равно вписаны в
    `stage2a.sql`. Номер выдаётся внутри транзакции создания - откатили
    запись, откатился и номер. `document_number_counters` больше не
    используется (остался от старого сайта); страница шаблонов показывает
    следующий номер по `counters`. На `documents.document_number`
    частичный уникальный индекс (`where document_number is not null`):
    занятый ручной номер даёт ошибку у поля, а не 500. В `substring(x
    from $1)` параметр обязательно с `::int`, иначе Postgres читает его
    как шаблон регулярки (поймано `check:db-rules`). LIKE по номерам
    больше нигде нет.
44. **Двойной заказ.** Страница оформления кладёт в форму скрытый
    `checkoutToken` (uuid), `placeOrder` пишет его в
    `orders.checkout_token` (уникальный индекс). Повтор с тем же ключом и
    тем же клиентом - редирект на уже созданный заказ, и это проверяется
    раньше корзины и лимита (после первого заказа корзина пуста); при
    параллельном повторе вторая транзакция падает на индексе, откатывается
    целиком (с промокодом) и тоже ведёт на первый заказ. Аналогично
    «заказ из КП»: `commercial_offers.external_order_id` + `FOR UPDATE`
    на КП; из отклонённого и просроченного КП заказ не заводится.
    Заказы из КП, созданные до этого поля, привязывает
    `recalc-accounting` (шаг 0: по описанию «По коммерческому
    предложению <номер>»; в отчёте - «КП, привязанных к уже созданным
    заказам»), поэтому на боевой он должен отработать до запуска нового
    приложения. Принятое КП без привязки кнопки «создать заказ» не
    показывает.
45. **Снимок заказа.** При оформлении в `order_items.item_name` пишется
    «Название, Характеристика: значение, …», в `order_items.unit` -
    единица, в `contact_info` - `is_corporate`, `company_name`, `inn`,
    `kpp`, `legal_address` покупателя (`lib/order-snapshot.ts`;
    `parseContact` отдаёт их как `buyer`). `lib/upd.ts` берёт снимок
    раньше текущих данных товара и профиля; у старых заказов снимка нет
    - как раньше. Позиция заказа с сайта, которую менеджер правит с тем
    же товаром, снимок не теряет. Чистое название товара без характеристик
    лежит отдельно в `order_items.product_name`: аналитика «что продаём»
    группирует по `coalesce(products.name, product_name, item_name)`, иначе
    у удалённого товара продажи раздробились бы по вариантам. У старых
    строк `product_name` пуст.
46. **Скидка в счёте и УПД не бывает отрицательной строкой.** Если итог
    заказа меньше суммы позиций, разница делится по строкам
    пропорционально сумме, копеечный остаток уходит в последнюю строку
    (`lib/upd-rows.ts`, BigInt в копейках; `check:upd`), цена за единицу
    = новая сумма / количество. Наценка (срочность, доставка) по-прежнему
    отдельная строка. `UpdData.extra` теперь всегда ≥ 0, `UpdData.discount`
    - скидка, ушедшая в строки; счёт печатает об этом строку.

48. **Производство: порядок, пауза, «Готов к выдаче».** Логика - в
    `lib/production-db.ts` (`startProductionOf`, `advanceProduction`,
    `setProductionHold`), действия в `admin/production/actions.ts` - тонкие
    обёртки с правами. Этапы идут по `(sort_order, id)`, текущий - первый
    «в работе», следующий - первый «ожидает» после него по позиции
    (`nextStageIndex` в `lib/production.ts`): новые этапы раньше получали
    порядок 0, и строгое «больше» перепрыгивало через все, кроме первого.
    Новый этап получает порядок `max + 10` (пустое поле в справочнике),
    у существующего пустое поле порядок не меняет. `advanceProduction` и
    `setProductionHold` берут `FOR NO KEY UPDATE` на производственный
    заказ **до** чтения этапов; на паузе, отменённом и завершённом заказе
    отказывают понятным текстом. Действия - `useActionState`
    (`ProductionForms.tsx`): раньше любой отказ был молчаливым `return`.
    Финал производства ставит заказу **`ready` («Готов к выдаче»)** вместо
    `completed`; дальше менеджер сам ставит shipped/delivered/completed.
    Значение добавлено в `orders_status` и
    `external_orders_production_status` (ALTER TYPE ... ADD VALUE),
    переходы: `in_work`/`processing` → `ready` → shipped/delivered/
    completed/cancelled, `ready` → `in_work`. Возврат `ready`/`completed` →
    `in_work` переоткрывает завершённое производство (`changeOrderStatus`):
    последний этап снова «в работе», производство `in_progress`, запись
    `returned` в журнале этапов. Порядок блокировок везде «заказ →
    производственный заказ» (в `advanceProduction` тоже), иначе финал и
    отмена заказа ждали бы друг друга по кругу. Склад: «остаток → материал
    → оповещения» (`saveMaterial` блокирует остаток первым), закупка:
    «закупка → позиция → остаток». `changeOrderStatus` получил
    `onlyFrom`: заказ, который менеджер уже отправил или закрыл руками,
    цех назад в «В работе» / «Готов» не тянет (запуск такого заказа в цех
    отказывает). Клиенту уходит «Новая стадия: Готов к выдаче» с пометкой
    (`notifyOrderStatus({ note })`, `statusNote`).
49. **Закупки.** Приёмка (`receivePurchaseItem`, `lib/purchases-db.ts`)
    пересчитывает `materials.cost_per_unit` средневзвешенно:
    `(остаток × старая + принято × цена) / (остаток + принято)`; нет
    остатка или старой цены - цена закупки; нулевая цена закупки цену не
    трогает. **Цена прихода включает долю доставки закупки**
    (`landedUnitPrice`: доставка делится между позициями пропорционально
    сумме и на заказанное количество) - доставка реально входит в
    стоимость материала на складе. Цена читается после `applyMovement`
    (он держит блокировку строки остатка), поэтому две приёмки одного
    материала считают среднее по очереди. Движение приёмки - тип
    **`purchase`** (раньше `order`, и номер закупки путался с номером
    заказа менеджера). **Оплата закупки**: действие «Отметить оплату»
    (`markPurchasePaid`) заводит общий расход (`general_expenses`) в
    категории «Закупка материалов» (создаётся при первой оплате) со
    ссылкой `general_expenses.purchase_order_id`; `purchase_orders.paid_amount`
    и `payment_status` - сумма и статус из таких расходов
    (`recalcPurchasePayment`), переплата отклоняется. Отдельной таблицы
    оплат нет: расход и есть запись об оплате, колонки `paid_amount` и
    `payment_status` в закупках уже были. **Права**: отметить оплату -
    нужны оба, `materials.edit` и `finance.create` (у менеджера второго
    нет, права не расширяли); отменить оплату - `materials.edit` и
    `finance.delete` (администратор). Расход оплаты закупки нельзя удалить
    из бухгалтерии отдельно (`deleteGeneralExpenseRow`) - только отменой
    оплаты на закупке.

    `verifyTotp`: вход (`auth.ts`), подтверждение включения, отключение
    (теперь пароль + код). Счётчик сбрасывается при смене секрета и
    отключении. Админ без 2FA видит баннер в `admin/layout.tsx`
    (`session.user.totpEnabled`), без блокировки. Код привязки Telegram -
    10 знаков без похожих символов, кнопкой в профиле
    (`issueTelegramLinkCode`), sha256 в `telegram_link_codes` на 15 минут,
    одноразовый (`DELETE ... RETURNING`); один активный код на пользователя
    (выдача под `pg_advisory_xact_lock(7002, userId)`, иначе две выдачи разом
    оставляли два живых кода). Лимиты `telegramConnect` (по чату) и
    `telegramLinkIssue` (по пользователю), письмо о привязке (из вебхука
    уходит через `afterResponse`, неудача - в лог). Регистрация сразу входит
    в аккаунт, поэтому «адрес занят» раскрывается осознанно; защита - лимиты
    `register` (3/15 мин) и `registerDay` (10/сутки) по IP.
    `users.session_version` -> JWT `sv`; сверка в колбэке `session`
    (`lib/session-policy.ts`) без лишнего запроса. Растёт
    (`bumpSessionVersion`) при смене/сбросе пароля, отключении 2FA,
    блокировке, «Выйти со всех устройств» (`logoutEverywhere`). Сессия
    сотрудника 7 дней от входа (`token.loginAt`), клиента 30. После
    выкладки сотрудники один раз войдут заново. Повторные подтверждения
    (текущий пароль, код) - лимит `reauth:<userId>` до bcrypt; ключ
    **общий** у смены пароля и отключения 2FA, поэтому `changePassword`
    снимает счётчик только после успешного UPDATE, а не на верном пароле
    (иначе знающий пароль получал бы свежие пять попыток на код). Проверки:
    `check:totp`, `check:session`, `check:telegram`.
54. **Права CRM и контрагентов.** Модули `crm` и `counterparties` (раньше
    `users.*`). Данные - копия действий с `users` (admin: create/delete/edit/
    manage/view, manager: view); `users` остаётся за клиентами и
    блокировкой. Сверка Точки - `finance.edit`. Экрана редактора прав нет -
    данные `role_permissions`, `scripts/seed-permissions.mjs` знает новые
    модули. **На проде** их выдаёт `scripts/grant-module-permissions.mjs`
    (см. п. 68). Перенос лида в контрагента требует `crm.edit` И
    `counterparties.edit`. `check:admin`.
55. **Исполнитель и ответственный - только сотрудник.** `STAFF_ROLES`
    (`lib/staff.ts`), `isActiveStaff`/`staffOptions` (`lib/staff-db.ts`:
    admin/manager, не заблокирован). Клиента в исполнители не поставить.
56. **Действия над клиентами (`admin/clients/actions.ts`).** Учётку admin
    трогает только admin (`loadTarget`; кнопки на странице клиента для
    не-админа скрыты по тому же правилу), себя не заблокировать, блокировка
    увеличивает `session_version`, все действия в журнале
    (`user.block/unblock/editor_access/warehouse_access/reset_link`).
57. **Печатные формы.** Предупреждения о реквизитах и ссылка в админку -
    только сотруднику (`access.isStaff`). Кабинет показывает по заказу
    только `docType = outgoing`.
58. **Журнал: любое действие админки, пишущее в БД, вызывает `audit()`.**
    `check:admin` падает на действии без `audit(` (исключения - `NOT_AUDITED`
    там же). Новому действию - подпись в `ACTION_LABEL` страницы журнала.
    `can()`/`staffOnly()`/`permissionsOf()` - через `React.cache`: одно
    чтение сессии и один запрос прав на запрос; `permissions.ts` не
    импортирует `next/headers`.
59. **Уведомления в два слоя (`lib/notify.ts`).** `deliverUser`/
    `deliverStaff` отправляют сразу и возвращают `{sent, failed, permanent}`
    (для планировщика); `notifyUser`/`notifyStaff` и готовые `notify*`
    откладывают через `afterResponse` (`lib/notify-after.ts`, `after()` из
    `next/server`). Каналы параллельно, ошибки логируются. Вне запроса
    задача идёт сразу; для node-скриптов заглушка `next/server` в
    `scripts/alias-hooks.mjs`. Новые события - в `lib/notify-events.ts`, в
    справочник - `npm run seed-notification-events` (зовёт `deploy.sh`).
    `notification_events`/`notification_subscriptions` приложение не читает:
    `notifyStaff` шлёт всем admin/manager с телеграмом.
60. **Планировщик: `POST /api/cron/run`** (`lib/cron-db.ts`, чистое -
    `cron-due.ts`, секрет - `cron-auth.ts`). `Authorization: Bearer
    $CRON_SECRET`; нет секрета - 404, неверный - 401. Зовёт контейнер cron
    (`scripts/cron.sh`, раз в 300 с). Без наложения:
    `pg_try_advisory_xact_lock`. Задачи: напоминания CRM и сроки задач
    исполнителю (только телеграм), уборка `rate_limits` и
    `telegram_link_codes`. «Один раз» = колонка с уже сообщённым сроком
    (`crm_reminders.notified_remind_at`, `tasks.notified_due_date`); отметку
    ставит сам SQL (`set notified_x = remind_at`), а не JS-дата: `Date` теряет
    микросекунды, и «почти равное» значение вечно считалось бы другим. Окна:
    напоминание до 3 суток после срока; задача от -24 ч до +3 суток. Не
    доставлено - повторим, но не бесконечно: безнадёжные ошибки Telegram
    (бот заблокирован, чата нет - `isPermanentTelegramError`) сразу ставят
    отметку, а прочие сбои - не больше `LIMITS.cronRetry` (12 попыток,
    счёт в `rate_limits` по ключу `reminder:<id>:<срок>`), потом отметка.
    Новая задача - функция в `cron-db.ts` + строка в `runCron`,
    идемпотентная. `check:cron`. **НЕ запускать полный проход на dev-базе с
    живыми данными** (настоящие Telegram и SMTP). `CRON_SECRET` в `.env`
    продакшена (`openssl rand -hex 32`).
61. **Отзывы и цена «от».** Отзыв только по заказу в shipped/delivered/
    completed (`lib/reviews.ts`), на новый - `notifyNewReview`. Цена «от» в
    каталоге, карточке, избранном и `/api/products` (поле `fromPrice`) -
    `fromUnitPrice` (`lib/product-price.ts`): цена за штуку при минимальном
    тираже, округлённом до кратности.
62. **Срыв уведомлений сотрудникам.** Действия клиента, которые шлют
    сотрудникам телеграм, ограничены: обращения и ответы - `LIMITS.ticket`
    (10/час на пользователя), сообщения в заказе - `orderMessage` (30/час),
    макеты - `upload` (50/сутки). Серия подряд схлопывается в одно
    уведомление: `claimStaffNotice("ticket:<id>" | "order:<id>" |
    "upload:<userId>")` пускает первое за 10 минут, остальное сотрудник видит
    в самом обращении/заказе/карточке.
63. **Проверка принадлежности словарю - `isKeyOf` (`lib/guards.ts`), не
    `raw in DICT`.** `in` смотрит по цепочке прототипов: `constructor`,
    `toString`, `__proto__` проходили как «известный статус». Новый код:
    `isKeyOf(DICT, raw)` (сужает тип до ключа) или `Object.hasOwn`. Это
    касается статусов, категорий, ролей, фильтров страниц, действий.
    `check:input` ищет по `src` оставшиеся `x in CONST` и падает на них.
64. **Даты из форм - только `parseCalendarDate` (`lib/dates.ts`).**
    Регулярки мало: `2026-02-31` ей соответствует, Postgres такое
    отвергает (500), а `new Date` молча сдвигает на 3 марта. Функция
    собирает дату обратно и сверяет (round-trip), год 1900-2200.
    `parseCalendarDateTime` - для `datetime-local` (местное время),
    `calendarDateAtNoon` - день как момент для колонок `timestamp`
    (полдень, не съезжает на соседнее число). Пустая необязательная дата -
    «нет границы», а **непустая и невозможная - ошибка в `fieldErrors`**,
    не молчаливый `null`. `check:input` падает на голой регулярке даты в
    `src`.
65. **Длина текстовых полей - `rejectOverlong(formData)` (`lib/text-limits.ts`).**
    Первая строка каждого серверного действия, читающего свободный текст:
    `const tooLong = rejectOverlong(formData); if (tooLong) return tooLong;`
    Предел задан по имени поля одним словарём: имя/тема/почта 255 (varchar),
    телефон 50, адрес 1000, теги 500, свободный текст (сообщение, описание,
    комментарий, заметки) 5000, HTML шаблона/схема полей/JSON позиций 100000,
    id, числа, даты и перечисления 64. Колонка короче словаря - свой предел
    вторым аргументом: телефон профиля 20, описание файла 500, текст
    напоминания 500, пункт чек-листа 500, примечание позиции закупки 500,
    код промокода 50, реквизиты компании 255 (`settings.value`). Ответ
    содержит `ok:false`, `message`, `error` и `fieldErrors` разом - годится
    любому состоянию формы; у состояния с `ok?: string` (склад) берут
    `tooLong.error`. Действие, которое читает текст и не зовёт
    `rejectOverlong`, роняет `check:input`. Старые `.slice(0, N)` остались
    как второй рубеж. Где zod со своим `.max()` - он точнее, словарь лишь
    не пускает мусор раньше.
66. **Загрузка макетов клиентов - не серверным действием, а потоком:
    `POST /api/client-uploads`.** Тело запроса - сами байты файла (не
    multipart: его потоком не разобрать), метаданные в заголовках
    `X-File-Name`, `X-Description` (оба `encodeURIComponent`), `X-Order-Id`.
    Файл пишется на диск через `saveUploadStream` (`lib/uploads.ts`)
    с счётчиком байт на лету: больше 50 МБ - поток обрывается и недописанный
    файл удаляется; предел считается по фактическим байтам, а не по
    `Content-Length`. Права как раньше (`currentUser`, заказ - свой).
    Лимиты: файл 50 МБ, **квота клиента 1 ГБ** суммарно по `client_uploads`
    (`CLIENT_UPLOAD_QUOTA`; проверяется до загрузки и ещё раз под
    `pg_advisory_xact_lock(7001, userId)` в `insertUploadWithinQuota`,
    иначе две параллельные загрузки обе видели бы свободное место),
    **50 файлов в сутки** (`LIMITS.upload` в `rate_limits`; считается и
    удалённый потом файл). Маршрут исключён из матчера `src/proxy.ts`:
    proxy буферизует тело запроса в памяти (`proxyClientMaxBodySize`).
    Клиентская форма (`client/uploads/UploadForm.tsx`) шлёт `fetch` с
    `File` телом. Действие `uploadClientFile` удалено. Другие места
    загрузки: фото брака (`quality.ts`, администратор) и картинки товара
    (`admin/products`) - серверными действиями, их может слать только
    сотрудник с правом.
67. **`serverActions.bodySizeLimit` = 10 МБ** (было 55). После переноса
    макетов самое тяжёлое в действиях - фото брака до **8 МБ**
    (`MAX_QC_PHOTO_SIZE`, было 10) и пачка картинок товара до **9 МБ
    вместе** (`MAX_PRODUCT_BATCH_SIZE`; одна картинка по-прежнему до 8 МБ;
    форма проверяет сумму до отправки, действие - после); плюс 10-20 КБ
    служебных байтов multipart. `proxyClientMaxBodySize` тоже 10 МБ. Менять
    лимит осторожно: превышение даёт общую ошибку Next, а не нашу подсказку.
    `check:input` сверяет, что обе админские загрузки влезают в лимит.
68. **Права на проде: `scripts/grant-module-permissions.mjs`** (`npm run
    grant-module-permissions`). Копирует каждой роли действия с `users` в
    `crm` и `counterparties`. Идемпотентно и **разово**: отметка
    `migration.crm_counterparties_permissions` в `settings` не даёт
    деплою возвращать права, которые администратор потом забрал
    (`--force` повторит). Пустая `role_permissions` (первая установка) -
    ничего не делает и отметку не ставит. `deploy.sh` зовёт шаг 6b после
    `drizzle-kit push` и до старта нового app; ошибка останавливает деплой.
    `first-install.sh` зовёт его ещё раз после `seed-permissions`.
69. **`.gitattributes`: `*.sh text eol=lf`.** Скрипты запускаются в
    Linux; CRLF в конце строки ломает shebang. В индексе все `.sh` уже в LF.
70. **CI - `.github/workflows/ci.yml`.** Две задачи на push и pull request:
    `static` (`npm ci`, `next typegen`, `tsc --noEmit`, `eslint
    --max-warnings=0`, `next build` с фиктивными окружением) и `checks`
    (сервис `postgres:17`, схема через `drizzle-kit push --force`, затем
    `npm run check`). `--force` нужен из-за `strict: true` в
    `drizzle.config.ts`: без него push ждёт подтверждения с клавиатуры.
    Push на пустую базу проходит без вопросов, stdin закрыт (`< /dev/null`).
    Проверено локально на пустой базе `postgres:17`: весь `npm run check`
    проходит. Для этого две проверки, зависевшие от данных рабочей базы,
    сделаны самодостаточными: `check:production-stock` заводит свои этапы
    цеха, если активных меньше двух (и убирает), а `check:admin` не требует
    прав на crm/counterparties там, где у роли нет прав на `users`. Секретов в
    CI нет: SMTP/Telegram/Turnstile не заданы, отправки невозможны.

## 6. Что уже сделано

### Витрина

Главная, каталог, карточка товара (с ценами по тиражам, характеристиками
и отзывами), о компании, контакты с формой обратной связи, требования,
оплата и доставка, FAQ, избранное, корзина, **оформление заказа**,
политика, условия, вход, регистрация, восстановление пароля.

**Оформление заказа** - `/checkout`. Контакты подставляются из профиля,
есть срочность (+50 %) и промокод с проверкой до отправки. Итог считает
сервер по ценам из базы: то, что показано в браузере, ни на что не
влияет. Заказ, позиции, запись о промокоде и бухгалтерская карточка
пишутся одной транзакцией, корзина чистится, сотрудникам уходит
уведомление. Требуется вход: колонка `orders.user_id` обязательная.

**Отзывы** - оставить может только тот, кто этот товар заказывал, по
одному на товар; публикуются после модерации в админке.

**Карточка товара** считает сумму за тираж прямо в браузере - той же
формулой, что корзина (`lib/product-price.ts`), с подсказкой про
следующую ступень. Галерея переключает фото по превью; пока фото работ
нет, показывает логотип. Для поисковиков - разметка `Product`, для
мессенджеров - `openGraph` с картинкой; на главной - `LocalBusiness`
(`lib/json-ld.ts`). Иконки, манифест и общая картинка для соцсетей лежат
в `src/app` (`icon.png`, `apple-icon.png`, `opengraph-image.png`,
`manifest.ts`), перегенерируются из `public/logo.svg`.

**Телефон в шапке** - значком, а на широком экране номером; в мобильном
меню первой строкой. **Страницы ошибок и загрузки** - у витрины и
админки свои `error.tsx`/`loading.tsx`, плюс `global-error.tsx`.

### Кабинет клиента

Сводка, заказы (обоих типов), карточка сайтового заказа с чатом и
файлами, карточка менеджерского заказа, мини-склад (по флагу),
поддержка, профиль со сменой пароля, привязкой телеграма и
**двухфакторным входом** (сотрудникам), редактор открыток (по флагу).

**Заказы обоих типов.** Сводка и список считаются по объединённому
набору (`src/lib/client-orders-db.ts`): сайтовые заказы - по
`orders.user_id`, менеджерские - через контрагента, привязанного к
аккаунту. У менеджерского заказа своя страница
`/client/orders/external/[id]` без себестоимости и маржи.

**Документы клиенту показывает менеджер.** У `orders` и
`external_orders` есть флаг `documents_visible`, по умолчанию выключен.
Пока он выключен, клиент видит в карточке заказа только надпись «Счёт и
УПД появятся здесь, когда менеджер согласует состав и сумму», а страницы
печати отвечают ему 404. Включает менеджер кнопкой в карточке заказа.
Сотруднику документы видны всегда. Правило проверяется скриптом
`check:documents`.

### Админка

Сводка, заказы с сайта, заказы менеджера, товары, клиенты,
**контрагенты**, производство, качество, задачи, склад, закупки,
**подрядчики**, бухгалтерия, аналитика, калькулятор, прайс-лист,
предложения, CRM, поддержка, сообщения с сайта, промокоды, документы,
шаблоны, Точка Банк, реквизиты, **справочники**, SEO, телеграм.

Что заводится и правится: контрагент, подрядчик, заказ менеджера и его
позиции, состав заказа с сайта, товар с категорией, ценами по тиражам
и картинками,
материал, закупка, расход, платёж, общий расход, промокод, КП, документ,
задача, лид, обращение, проверка качества, дефект, файл, позиция
мини-склада, движение материала и списание на заказ, ответ в переписке
по заказу, категории товаров, статьи расходов, разделы документов.

**Картинки товара** - в карточке товара в админке. Логотип показывается
в каталоге и в избранном, один на товар: новый вытесняет прежний вместе
с файлом. Фотографии готовых работ показываются только в карточке
товара, первая загруженная становится главной, главную можно переназначить.
Разделение стоит в колонке `product_images.kind` (`logo` / `photo`).

Файлы лежат в `storage/uploads/products/` и отдаются открытым маршрутом
`/api/product-image/[name]` - проверки прав там нет намеренно, это
витрина, но имя файла проверяется по образцу. В `public/` их не кладём:
`public/` вшивается в образ при сборке, а хранилище примонтировано томом
и переживает обновление.

Пачкой картинки заводит `scripts/import-product-images.mjs`: кладёте
файлы в `assets-src/products/logos/` и `assets-src/products/photos/`,
называя их по id товара (`101-vizitki.png`, или папка `photos/101/`),
скрипт ужимает их в WebP, раскладывает по хранилищу и заводит записи.
Перенесённые исходники уезжают в `_imported/`, поэтому повтор запуска
ничего не задваивает. Подробности - `assets-src/products/README.md`.

**Сводка админки - «на сегодня»**: просроченные заказы менеджера, что
сдавать сегодня и завтра, кто не заплатил, новые заказы с сайта, задачи
просроченные и на сегодня, новые сообщения и обращения. Разделы - по
правам роли. Просрочка считается одним правилом `isExternalLate`
(`lib/external-orders.ts`): день срока ещё не просрочка; в списке заказов
менеджера просроченный срок подсвечен.

**Журнал действий** - `/admin/audit`, по правам на настройки. Фильтр по
сотруднику, разделу и коду действия; подписи действий и ссылки на
сущности - словари в самой странице. Новое действие без подписи
показывается кодом, а не пропадает.

**Справочники без базы**: характеристики товара с надбавками - в
карточке товара (`attribute-actions.ts`, первое значение выбрано на
витрине по умолчанию, поэтому первым ставят базовое); этапы производства -
в «Справочниках» (удаления нет, этап выключают: по нему лежит история);
шаблоны документов - `/admin/documents/templates/[id]` и `/new`, с
проверкой схемы полей (`lib/document-templates.ts`) и превью через
`safeDocumentHtml`.

**Контрагенты** (`clients`) - заказчики без аккаунта на сайте. Заводятся
при оформлении заказа менеджером и выбираются в следующем. Привязка к
аккаунту одним действием тянет в кабинет все их заказы; осиротевший
заказ цепляется к контрагенту в своей карточке. Удаления нет - архив.

**Заказ менеджера** - `/admin/external-orders/new`: заказчик из
справочника или новый, позиции с признаком перезаказа и подрядчиком,
себестоимость строки, маржа, срок, оплата. Бухгалтерская карточка,
расчётная себестоимость и налог считаются той же транзакцией. В карточке
заказа правятся шапка и позиции, списываются материалы, заказ
запускается в производство и удаляется (администратору).

**Перезаказ** - признак стоит на позиции, а не на заказе: заказ уходит
на сторону то целиком, то частью. Маржа строки = `price − expense_amount`,
в итогах видно «ушло подрядчикам».

**Производство** - одна машина стадий на оба типа заказов:
`production_orders` принимает и `order_id`, и `external_order_id`. На
доске очередь и колонки по этапам, из очереди заказ запускается в цех.
Поле `external_orders.production_status` осталось для заказов, которые в
цех не отдают. Последний этап переводит заказ в «Готов к выдаче», пауза и
отмена блокируют продвижение, отказы видны в форме (см. п. 48).

**Бухгалтерия** - расходы и платежи по карточке заказа, общие расходы.
Оплата считается из платежей: статус карточки и самого заказа
пересчитываются вместе, а не ставятся руками.

**Документы** - УПД по постановлению 1137 (19 колонок), счёт с платёжным
QR по ГОСТ Р 56042-2014, печать КП. Всё печатается через диалог браузера
вместо Dompdf. Маршруты: `/print/invoice/[source]/[id]`,
`/print/upd/[source]/[id]`, где `source` - `site` или `external`,
и `/print/offer/[id]`. Реквизиты покупателя у менеджерского заказа
берутся из контрагента; КПП контрагентам не заводим.

**Права** - у администратора открыты все действия во всех модулях, меню
админки фильтруется по правам роли, в шапке витрины есть кнопка
«Админка» для сотрудников.

**Уведомления клиенту - в телеграм и на почту**, по галочкам в профиле
(`users.email_notifications`, `telegram_notifications`). Письмо собирается
из того же текста, что телеграм (`lib/notify-format.ts`), кнопки
становятся ссылками; каждая попытка пишется в `notification_log` со своим
каналом. Сотрудникам - только телеграм.

**Уведомления** - новый заказ с сайта и новый заказ менеджера
сотрудникам, смена статуса и стадий производства клиенту, переписка по
заказу в обе стороны. Всё через телеграм, с журналом в
`notification_log`.

**Журнал действий** - `src/lib/audit.ts`, пишет в `audit_log`: заказы,
позиции, цены, права, деньги, контрагенты, подрядчики, документы, КП,
промокоды, второй фактор. Ошибки записи глотаются: заказ уже создан, и
падать на строчке журнала нельзя.

### Безопасность (сверка со старым сайтом + пентест)

Полная сверка и отчёт о локальном пентесте - в `SECURITY.md`. Кратко:
всё, что защищало старый сайт, перенесено или сделано надёжнее.
Доработано: восстановлена сложность пароля (`lib/password-policy.ts`),
добавлен отсев одноразовой почты (`lib/email-guard.ts`), вебхук телеграма
в проде обязателен-с-секретом, промокоды под ограничением частоты,
`allowedOrigins` для серверных действий (домен из `SITE_DOMAIN`), предел
тела действий/прокси - 10 МБ (макеты клиентов до 50 МБ идут отдельным
маршрутом потоком, см. §5 п. 66-67). Стережёт `npm run check:security`.

**Капча Cloudflare Turnstile** на входе и регистрации (`lib/turnstile.ts`,
`components/site/Turnstile.tsx`). Виджет и проверка включаются, только
если заданы ключи: публичный `NEXT_PUBLIC_TURNSTILE_SITE_KEY` (вшивается
в сборку - на dev пустой, иначе боевой ключ на localhost не проходит) и
серверный `TURNSTILE_SECRET_KEY`. Реальные ключи из старого проекта лежат
в `.env.production.example`. В CSP добавлен `challenges.cloudflare.com`
(frame-src, connect-src).

**Отзыв всех сессий при смене пароля.** Колонка `users.password_changed_at`;
в токен при входе кладётся её значение (`token.pwdAt`), а колбэк `session`
сверяет с базой на каждом чтении - токен, выписанный до смены, становится
недействителен. Ставится в `resetPassword` и `changePassword`. После
смены в кабинете человека уводит на `/login?reason=password-changed` с
понятным сообщением: текущая сессия тоже сбрасывается.

Менеджер видит загруженные клиентом макеты прямо в карточке заказа с

существующем чате заказа.

### Прочее

- **Телеграм-бот:** вебхук, команды, уведомления с журналом. Привязка
  разовым кодом (HMAC от номера, 15-минутного окна и `AUTH_SECRET`)
  вместо дыры старого сайта, где чат привязывался по одной почте.
- **SEO:** генерируемые `sitemap.xml` и `robots.txt`, канонические
  ссылки, `metadataBase`, настройки страниц в админке.
- **Редиректы** со всех живых адресов старого сайта -
  `src/lib/redirects.ts`, 159 правил, плюс подмена адреса вебхука
  телеграма (не редирект: на 301 телеграм повторил бы POST как GET).
- **Безопасность:** CSP с одноразовым ключом в `src/proxy.ts`,
  ограничение частоты попыток в `src/lib/rate-limit.ts` (вход,
  регистрация, форма связи, восстановление пароля, привязка телеграма,
  оформление заказа), отпечаток вместо самой ссылки на смену пароля,
  выключен `X-Powered-By`, двухфакторный вход сотрудников.
- **Двухфакторный вход:** TOTP по RFC 6238 своей реализацией
  (`lib/totp.ts` - это HMAC-SHA1 и четыре строки арифметики, ради них
  зависимость не нужна). Настройка в профиле в два шага: секрет и QR,
  потом подтверждение кодом. Пока код не подтверждён, вход его не
  спрашивает - иначе человек, закрывший вкладку, запер бы себя сам.
  Поле кода на входе появляется, только когда сервер его спросил.
- **Развёртывание:** `Dockerfile`, `docker-compose.yml` (приложение, база,
  Caddy и ночные бэкапы), `Caddyfile` с редиректом www → голый домен,
  `README.md` с порядком переключения.
- **Бэкапы:** сервис `backup` в `docker-compose.yml` и
  `scripts/backup.sh` - дамп базы в `./backups` в 3:00, хранение 14 дней,
  недоделанный файл удаляется. Рядом - архив тома `uploads` (макеты,
  фото брака, картинки каталога), хранение 7 дней
  (`BACKUP_UPLOADS_RETAIN_DAYS`): без него дамп неполон. Дамп - формат
  custom (`bzk-….dump`), до него были `….sql.gz`. Восстановление - только
  `bash deploy/restore.sh [файл]`, см. §5 п. 38. Необязательная выгрузка
  копий вне сервера через rclone (`RCLONE_REMOTE`) - в DEPLOY.md.

**Матрица прав** (таблица `role_permissions`, модули: `orders products users

- `admin` - все четыре действия во всех модулях плюс `users manage`,
  49 строк. Дозаполняет `node scripts/seed-permissions.mjs`,
  скрипт идемпотентен.
- `manager` - `orders create/edit/view`, `products view`, `users view`,
  `finance view`, `materials create/edit/view`, `documents create/edit/view`,
  `tasks create/edit/view`, `kanban edit/view`, `messaging create/view`,
  `calculator create/view`, `pricelist view`. Права на `settings` у него
  нет, поэтому в меню он не видит промокоды, реквизиты, справочники, SEO
  и телеграм.

**Порядок ручной проверки в браузере:**

1. Сначала проверить, не открыта ли уже сессия: кука входа переживает
   перезапуск сервера, и в шапке видно имя. Если сессии нет -
   `node scripts/dev-password.mjs set` - временный пароль задаёт этот
   скрипт (администратор `USER_ID` из него же; адрес администратора -
   у заказчика), а после проверки `node scripts/dev-password.mjs restore`. **Хеши в файлы не
   записывать** - скрипт берёт исходный из дампа. Скрипт работает только
   против локальной базы.
2. Тестовые строки удалять за собой, последовательности возвращать
   (`setval`).
3. `delete from rate_limits;` после проверок входа и форм.
4. `npm run verify-restore` - должен сказать «Всё восстановлено»
   (с поправкой на заказ № 18 заказчика, см. выше).
